# 结构化电脑操控：下期实施规划

## 结论

可行性评估为“中高”。Windows 提供 UI Automation、Win32、Shell 和系统媒体会话等稳定接口，能够完成一批明确、可审计的电脑操作；难点不在调用 API，而在权限边界、目标识别、误操作恢复和提示注入防护。

下一期只做结构化、白名单化操作，不提供任意 Shell、任意脚本或“模型直接移动鼠标并点击”的通用能力。

## 首期范围

### 建议纳入

- 打开已安装应用、文件夹、文件和 HTTPS 链接。
- 查询当前前台应用、运行中的普通桌面应用和显示器信息。
- 调整系统音量、静音状态，并复用现有媒体播放控制。
- 对明确窗口执行最小化、还原、置前和移动到指定显示器。
- 在用户指定文本后执行复制到剪贴板。
- 所有会改变系统状态的操作先展示结构化预览；高影响操作必须逐次确认。

### 暂不纳入

- 任意 PowerShell、CMD、注册表写入或下载后执行。
- 无明确目标的坐标点击、连续键盘宏和游戏内操作。
- 删除文件、卸载应用、结束系统进程、修改安全设置。
- 读取密码框、浏览器登录数据或未由用户选择的文件内容。
- 让网页、文档或屏幕内容自行授权新的工具调用。

## 建议架构

```text
用户请求
  → 意图分类（只产出结构化候选命令）
  → JSON Schema 校验
  → 本地策略与白名单检查
  → 风险分级 / 用户确认
  → C# 执行器（Win32、UI Automation、Shell API）
  → 结果核验
  → 脱敏审计记录
```

核心原则：

1. 模型只提出候选命令，不直接触碰系统 API。
2. 执行器拒绝 Schema 之外的字段、未知命令和模糊目标。
3. 目标通过进程 ID、窗口句柄、应用标识或规范化路径绑定，不能只依赖窗口标题。
4. 执行前重新验证目标仍存在，防止确认后窗口被替换。
5. 操作结果必须用系统状态回读验证，不能只把 API 返回成功当作完成。

## 权限与确认

| 等级 | 示例 | 默认策略 |
|---|---|---|
| 只读 | 查询前台窗口、列出显示器 | 可直接执行并记录 |
| 低影响 | 打开应用、播放暂停、移动窗口 | 首次确认，可按命令类型记住 |
| 中影响 | 关闭普通窗口、覆盖剪贴板 | 每次确认 |
| 高影响 | 文件删除、进程终止、系统设置修改 | 首期不支持 |

总开关默认关闭。记住授权时只记录精确命令类型，不允许用一次授权覆盖“所有电脑操作”。

## 分阶段实现

### A. 契约与只读探测

- 定义版本化命令 Schema、风险等级和结果类型。
- 实现前台窗口、应用列表、显示器查询。
- 建立白名单、确认卡片和脱敏审计。
- 为目标替换、过期确认、未知字段和提示注入编写拒绝测试。

验收：任何未注册命令均不能到达执行器；只读查询不会改变窗口或文件状态。

### B. 低影响执行器

- 打开应用/文件/链接。
- 音量、媒体和窗口移动。
- 每种命令实现执行后状态回读。
- 复用灵动岛显示“待确认、执行中、成功、失败”状态。

验收：每个操作均有成功、目标消失、权限拒绝和超时测试；失败不会自动改用更高权限方式重试。

### C. 有限 UI Automation

- 仅对用户明确选择的应用启用。
- 只暴露可识别的按钮、文本框和菜单项，不使用任意屏幕坐标。
- 展示即将操作的应用、控件名称和动作。
- 对控件树变化、同名控件和焦点劫持进行二次校验。

验收：目标控件不唯一或应用焦点变化时必须停止并重新确认。

## 预估工作量

- A 阶段：3–5 个开发日。
- B 阶段：4–7 个开发日。
- C 阶段：7–12 个开发日，取决于首批支持的应用数量。

建议下次先确认首批要控制的 3–5 类操作，再实现 A+B；不要一开始追求“什么软件都能控制”。
